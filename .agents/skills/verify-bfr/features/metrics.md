# Reproducible service measurements

[Hosted run 39732079698](https://github.com/STEVVVU/byzantine-erasure-storage/actions/runs/39732079698) passed all 180 batches, 15 repair samples and the 4 KiB stability stage. The root README and `docs/evidence/metrics-39732079698/measurement.json` retain all cells, expected quorum failures, latency tails, resources and archive hashes. Zero errors does not mean the scheduled rates were sustainable; requests queued in the client pool and trusted-state path. Faults stop servers rather than inject active Byzantine responses. Absolute repair/restart times have no matched repair-time baseline. The accepted 4 KiB profile still cannot diagnose the 1 MiB limiter. The maintained driver now schedules profiles and 60-second closed-loop stability at all frozen sizes, but the added 128 KiB and 1 MiB diagnostic stages are draft coverage and remain unrun; the hosted 4 KiB evidence is unchanged.

Run `python scripts/benchmark.py --run-id <fresh-id>` on isolated Ubuntu with the hash-locked runtime. Use `--smoke` only for short correctness validation, never published performance claims.

The maintained driver reuses Launch, Doctor and owned-process Cleanup. It uses four real disk-backed servers and the real CLI. Frozen input bytes follow `(i * 37 + 11) % 251`. Sizes are 4 KiB, 128 KiB and the supported 1 MiB limit. Five alternating runs compare a warm signed/quorum HTTP read with a trusted local disk read using the same Tahoe n4/k2 codec. The latter omits security and networking and is an overhead floor, not an equivalent storage system. Each side starts a fresh Python process and writes reconstructed output with fsync. Storage rows are aggregate snapshots over prior sample/repair files, taken before the current size's repair sweep; do not label them final footprint or per-file-only amplification.

Concurrency 1/4/8 and scheduled arrivals at 4 times concurrency per second include queue delay in tails. Full cells offer `max(32, int(rate * 10))` operations, while smoke retains two. Healthy, one stopped server and two stopped servers distinguish useful completions from expected quorum rejection. A two-server failure counts as expected only when the CLI reports the specific missing metadata quorum, exits2 and creates no output; unrelated CLI failures remain errors. Completed, rejected and erroneous requests have separate latency distributions with actual sample counts in `latency_by_outcome`; raw records remain intact. A timed-out operation remains an error and is separately counted as a timeout. Empirical p99 is omitted when an outcome has fewer than100 observations; even larger bounded cells do not establish a stable production p99. Every completion verifies exact source bytes. The separate exact-read cProfile excludes its instrumented timing from comparisons and records one size-qualified profile and usage receipt per size, retaining the original 4 KiB filenames. Full runs also perform a minimum 60-second closed-loop stability stage per size, retaining each read result and usage receipt; smoke remains 4 KiB only. Restart readiness, repair and storage bytes are retained. The server logs and raw samples survive cleanup. Read `environment.json`, `samples.json`, `summary.json` and the profiles before making a claim. Never infer formal security, WAN performance or Tahoe grid performance from these loopback measurements.
