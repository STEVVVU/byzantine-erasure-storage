# Reproducible service measurements

[Hosted run 39732079698](https://github.com/STEVVVU/byzantine-erasure-storage/actions/runs/39732079698) passed all 180 batches, 15 repair samples and the 4 KiB stability stage. The root README and `docs/evidence/metrics-39732079698/measurement.json` retain its cells, expected quorum failures, latency tails, resources and archive hashes. Expanded baseline [39747376867](https://github.com/STEVVVU/byzantine-erasure-storage/actions/runs/39747376867) completed all three exact-read profiles and three 60-second closed-loop stages. Its 180 batches retained 31,200 offers, 23,400 exact completions and 7,800 expected two-down quorum rejections, zero other errors/timeouts. Its raw hashes, medians and candidate request proof are in `docs/evidence/read-response-reuse-20261022/measurement.json`. Zero errors does not make scheduled rates sustainable. Faults stop servers rather than inject arbitrary Byzantine responses; repair timings have no matched repair baseline. Do not infer a speedup from different hosted campaigns.

The expanded 1 MiB profile identifies 36 `_request` calls: four metadata responses plus four full share responses for each of eight stripes. Requests took about 0.191 s cumulative inside a 0.239 s read; separate import startup also remained substantial. The reader's local response dictionary now avoids repeated successful downloads while retaining every stripe's envelope/digest/signature validation. Rejected cached responses are evicted, and no cache survives the read. `scripts/verify_read_requests.py --run-id <fresh-id>` proved exact 1 MiB bytes with eight actual HTTP requests and real codec execution; all owned cleanup passed. The unit regression failed with eight block requests instead of four before the change, then passed alongside the existing tests. The focused unit test stubs only decoding, while this driver and the normal/fault journey exercise the real decoder. Cached data may delay observing a repair of previously corrupt later-stripe bytes within that same read; do not claim availability equivalence under arbitrary mobile corruption. Throughput comparison remains pending.

Run `python scripts/benchmark.py --run-id <fresh-id>` on isolated Ubuntu with the hash-locked runtime. Use `--smoke` only for short correctness validation, never published performance claims.

The maintained driver reuses Launch, Doctor and owned-process Cleanup. It uses four real disk-backed servers and the real CLI. Frozen input bytes follow `(i * 37 + 11) % 251`. Sizes are 4 KiB, 128 KiB and the supported 1 MiB limit. Five alternating runs compare a warm signed/quorum HTTP read with a trusted local disk read using the same Tahoe n4/k2 codec. The latter omits security and networking and is an overhead floor, not an equivalent storage system. Each side starts a fresh Python process and writes reconstructed output with fsync. Storage rows are aggregate snapshots over prior sample/repair files, taken before the current size's repair sweep; do not label them final footprint or per-file-only amplification.

Concurrency 1/4/8 and scheduled arrivals at 4 times concurrency per second include queue delay in tails. Full cells offer `max(32, int(rate * 10))` operations, while smoke retains two. Healthy, one stopped server and two stopped servers distinguish useful completions from expected quorum rejection. A two-server failure counts as expected only when the CLI reports the specific missing metadata quorum, exits2 and creates no output; unrelated CLI failures remain errors. Completed, rejected and erroneous requests have separate latency distributions with actual sample counts in `latency_by_outcome`; raw records remain intact. A timed-out operation remains an error and is separately counted as a timeout. Empirical p99 is omitted when an outcome has fewer than100 observations; even larger bounded cells do not establish a stable production p99. Every completion verifies exact source bytes. The separate exact-read cProfile excludes its instrumented timing from comparisons and records one size-qualified profile and usage receipt per size, retaining the original 4 KiB filenames. Full runs also perform a minimum 60-second closed-loop stability stage per size, retaining each read result and usage receipt; smoke remains 4 KiB only. Restart readiness, repair and storage bytes are retained. The server logs and raw samples survive cleanup. Read `environment.json`, `samples.json`, `summary.json` and the profiles before making a claim. Never infer formal security, WAN performance or Tahoe grid performance from these loopback measurements.

For the matched client comparison, follow [the Hyperfine benchmark contract](../../../../docs/read-reuse-benchmark.md). `scripts/compare_read_reuse.py --run-id <fresh-id> --hyperfine <binary>` uses the same owned lifecycle, a frozen baseline client, five alternating pairs at each size, and exact output validation. The manual `read-reuse.yml` workflow preserves all native receipts; a comparison is pending until that run and its receipts are audited.
