The manual **Compare BFR read reuse with Hyperfine** workflow compares the frozen baseline `e1ce5826e82810f4154d0d7ced6906bb570ba963` with the candidate commit selected by the workflow. It runs both clients against the same four loopback servers, owner, stored file and reader state on one Ubuntu runner. The baseline is a detached Git worktree. Both sides use the same Python 3.11 environment installed from `requirements.lock`. The server, model, protocol constants, codec adapter, Tahoe codec, CLI entrypoint and runtime dependency files must match between commits, so the comparison measures end-to-end client changes under the same runtime and server behavior.

Each size uses bytes generated by `(i * 37 + 11) % 251` at 4 KiB, 128 KiB and 1 MiB. The writer creates one file per size, and the reader explicitly trusts its generated public key before either client reads. The script warms each arm once outside measurement, then runs five alternating baseline/candidate pairs, reversing the first arm on odd-numbered pairs. One complete `bfr.py read` CLI runs at a time. The timer includes Python and CLI startup, network and codec work, checkpoint updates, output writing and fsync. The source SHA-256 must match the decoded output after every warmup and measured invocation.

Hyperfine 2.0.0 owns each measured command's wall-clock timing, exit code and JSON receipt. The driver invokes one arm per Hyperfine command with exactly one run so it can alternate paired arms. Native per-invocation JSON files are retained with their hashes, exact CLI and Hyperfine commands, output hashes, baseline and candidate commit IDs, Python package inventory, locked requirements hash, host details and median/range summaries. Hyperfine also records CPU, user, system and peak resident-memory metrics when the runner exposes them. The profile stage is excluded from this comparison.

This is a warm, single-concurrency loopback CLI comparison. It does not measure offered rate, saturation, WAN behavior or production storage. Five samples per arm are suitable for a compact paired comparison but do not establish tail percentiles. A result is not a speedup claim until the workflow passes, all 30 timed outputs match the generated bytes, and the raw receipts show the same Hyperfine version and schema for both arms. A failed command or incorrect output fails the run. The comparison does not identify the limiter by itself; treat an unexplained difference as inconclusive and use the separate profile evidence to explain it. The workflow artifact is the primary measurement record; the compact reviewed result preserves selected native measurements and their hashes.
